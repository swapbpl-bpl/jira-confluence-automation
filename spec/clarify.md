# Specification Review: Gaps and Clarifications

- **Reviewed documents**: `spec/constitution.md`, `spec/specification.md`
- **Review date**: 2026-09-28
**Overall assessment**: The user workflow and safety intent are clear, but several decisions are needed before implementation can be estimated or reliably tested. The items below are ordered by implementation and stakeholder risk. References use requirement IDs and headings in `spec/specification.md`.

## P0 - Resolve Before Implementation

### 1. User identity and authorization are undefined

**References**: User Stories 1, 3, 4, and 5; FR-003; FR-023; Key Entities.

The spec identifies a Project Manager but does not say whether the app is single-user/private or multi-user, how users authenticate, who may view or edit drafts, or who may publish. Server-side credentials do not authorize individual users. This matters especially because reports contain issue details and publishing is an externally visible action.

**Clarify**: Is the deployment private to one trusted user, or must it support authenticated users and roles? Define access rules for configuration, report viewing/editing, and publishing, including audit attribution.

### 2. Sprint-close issue membership and status cannot be derived from the specified fields

**References**: FR-010, FR-011, FR-014; User Story 2, scenario 4.

FR-010 lists issue attributes but not sprint membership history, status transition history, or the data source for state at sprint close. Current issue status may differ from status at close, and issues may be added to or removed from a sprint after completion. FR-011 and the incomplete-work definition require a historical snapshot.

**Clarify**: Define the authoritative Jira endpoints/fields and as-of rule for sprint membership and status. Specify handling for post-close changes, reopened issues, issues moved between sprints, and unavailable changelog/history data. State whether reports use current data or a captured sprint-close snapshot.

### 3. Point and completion metric formulas are unspecified

**References**: FR-013, FR-017, SC-003; Summary Content in the source requirements.

“Committed points” and “completed points” have no calculation rule. The spec does not identify the Jira estimation field, whether subtasks count, how unestimated issues or estimate changes are handled, or whether completion means Done at close versus transitioned to Done during the sprint. SC-003 cannot be evaluated until these rules are explicit.

**Clarify**: Specify the point field, included issue types, sprint commitment cutoff, treatment of estimates changed after commitment, and the exact numerator and denominator for completion percentage. Define rounding and display rules for missing estimates and zero committed points.

### 4. Risk and blocker classification is not testable yet

**References**: FR-012, FR-018; Clarifications Needed: Stale/blocked threshold and Flagged issue detection.

The spec does not define calendar versus business days, timezone, the date from which staleness is measured, relevant status changes, or whether flags are evaluated at sprint close or report generation. It also does not define how Jira's native Flagged field and labels are interpreted, how duplicate risk causes are merged, or what “reason” is shown.

**Clarify**: Set the threshold and time basis, source timestamp, flag field/label values, as-of date, deduplication rule, and user-facing reason format. Define how an issue matching multiple risk rules is rendered.

### 5. Executive summary generation method and safeguards are missing

**References**: Summary; FR-016; User Story 2.

The specification says the system generates a plain-language overview but does not state whether it uses deterministic templates, an LLM, or another method. If generated by an LLM, provider, data handling, cost/availability behavior, grounding, and hallucination safeguards are unspecified. The constitution requires summaries to be derived from Jira data and not silently infer facts.

**Clarify**: Choose the generation method. If using an LLM, define approved provider/model, which Jira fields may be sent, prompt/output constraints, evidence or validation requirements, behavior on provider failure, and whether generated text is stored. Require the reviewer to be able to identify unsupported or missing data.

### 6. Stakeholder audience conflicts with internal appendix placement

**References**: Summary; FR-016, FR-018; Key Entities.

The report is intended for external/client stakeholders and internal PMO users, yet a single Confluence page is required to contain both a stakeholder-facing summary and a detailed appendix with issue keys and technical detail. No audience separation, page permissions, or redaction rules are defined. A heading or section break does not prevent external readers from seeing internal details.

**Clarify**: Decide whether the appendix is safe for the same audience and page permissions. Otherwise define separate pages/spaces or a configurable omission/redaction rule, and specify who can see each version before confirmation and after publication.

### 7. Jira and Confluence platform/authentication choices block integration details

**References**: FR-003 through FR-007; Clarifications Needed: Jira deployment.

Cloud versus Server/Data Center is unresolved, and Confluence deployment/authentication is not independently specified. API versions, authentication mechanisms, permissions, pagination, and response formats vary. The spec refers generally to server-side environment configuration but does not identify required setting names or validation behavior.

**Clarify**: Confirm Jira and Confluence deployment types and supported API versions/authentication. Define required configuration keys, validation/connectivity-check behavior, and how credentials are provisioned and rotated. Keep secrets out of persisted project configuration as required by FR-003.

## P1 - Resolve Before Detailed Design

### 8. Release reporting is deferred outside V1

**References**: Summary; FR-015, FR-026; Out of Scope for V1; constitution principle “Human-Controlled Publishing”.

V1 is defined as closed-sprint-only. Release/version reporting remains deferred until a separate scope update defines its selection, data, metrics, and acceptance criteria. The feature requirements and title convention now refer only to sprints for V1; the constitution's new-page rule will apply if release reporting is later added.

**Resolution**: No release/version reporting is included in V1. If added later, define its separate workflow and metrics, then apply the constitution's new-page rule to that report type.

### 9. Publish retry idempotency and ambiguous outcomes lack a mechanism

**References**: User Story 4, scenarios 4-5; FR-025, FR-027, FR-028; SC-006.

The spec requires retries not to duplicate pages but also permits a separate confirmed publish to create another page. It does not define how the application distinguishes those operations or handles a timeout after Confluence created a page but before the application recorded success. The same draft version could therefore produce duplicates or be incorrectly treated as already published.

**Clarify**: Define a durable publish-operation ID/idempotency key and the reconciliation strategy for uncertain outcomes (for example, lookup by a stored marker or title/parent plus operation identity). Specify whether a retry reuses an operation ID and how an intentional republish creates a new one. Define recovery if Confluence succeeds but PostgreSQL persistence fails.

### 10. Draft lifecycle, versions, and regeneration behavior are incomplete

**References**: User Story 2, scenario 5; User Story 3; FR-019 through FR-021; Key Entities.

The spec requires saved revisions and a draft version at publish time but does not define version creation, concurrent edits, generated-versus-reviewed content, regeneration for an existing sprint, or whether editing a previously published draft is allowed. Importing an externally edited Markdown file has no identity or conflict rules.

**Clarify**: Define draft states and revision rules, including whether generation creates a new draft or replaces an existing one; how published revisions remain immutable; how concurrent/stale edits are detected; and how an imported file is matched to a draft and handled when it is outdated or malformed.

### 11. Configuration ownership and the “connection check” workflow are unclear

**References**: User Story 1, independent test and scenarios; FR-004, FR-005; Clarifications Needed: Configuration administration.

FR-005 says the system supports configured service destinations, but it does not specify how they are configured. The acceptance test expects a Confluence destination check that is not otherwise required. The open question allows either environment-only settings or an administrator UI, which have different security and operational requirements.

**Clarify**: Choose deployment-time environment configuration or an authenticated admin workflow. If a connection check is in scope, define its permissions, result, and whether it creates/modifies anything (it should be read-only). Define which settings may be changed without restart and how configuration changes affect in-flight operations.

### 12. HTTP API contracts are absent

**References**: Constitution: Explicit Application Boundaries and Development Workflow; FR-002; all user stories.

The constitution requires documented, versionable frontend/backend API contracts, and the spec requires a browser-based workflow, but no endpoint surface, request/response schemas, validation errors, authorization behavior, or asynchronous-operation model is defined.

**Clarify**: Add or reference an API contract covering sprint listing, report generation, draft retrieval/update/import/export, publish confirmation/status, history, and any connection checks. Define error payloads, pagination, API versioning, and how the UI polls or receives progress.

### 13. Markdown conversion, preview fidelity, and content security need rules

**References**: FR-020, FR-021, FR-023, FR-024.

The spec requires Markdown editing/import, a content confirmation, and conversion to Confluence format, but does not define supported Markdown, unsupported syntax behavior, preview fidelity, HTML handling, or sanitization. Untrusted imported content rendered in the browser or converted to Confluence can create stored-script or unsafe-link risks.

**Clarify**: Define the supported Markdown subset, behavior for unsupported constructs, and whether the confirmation preview must match the published output. Require safe rendering/sanitization of imported Markdown and define allowed links/HTML. Specify upload size limits and validation if file import is the intended workflow.

### 14. Persistence, data minimization, and retention are unspecified

**References**: Constitution: Accurate, Traceable Reports and Secure Atlassian Integration; FR-019, FR-027; Key Entities.

“Relevant source data or snapshot needed” could mean persisting all issue summaries and assignees or only a minimal reproducibility record. The spec does not define retention/deletion, whether issue data is refreshed, database access controls, encryption/backups, or what happens when a Jira issue is later deleted or changed. This is especially important for personal data and external stakeholder reports.

**Clarify**: Specify the minimum retained Jira fields, retention and deletion policy, access controls, encryption expectations, backup/recovery, and whether reports are immutable snapshots or are regenerated from live data. Define how a report remains explainable after source data changes.

### 15. Pagination, scale, and partial failures are not covered

**References**: FR-007 through FR-010; Constitution: External service calls; User Story 2.

The specification requires all issues and closed sprints but does not require Jira pagination or define expected maximum sprint size, request concurrency, rate-limit backoff, partial-result behavior, or cancellation. FR-007 mentions handling transient errors without losing drafts but not whether partial data may be saved or published.

**Clarify**: Require complete pagination and define safe retry/backoff limits, request cancellation, and partial-failure behavior. A report with incomplete issue data should be marked incomplete and publishing should be blocked or require an explicit warning/override.

### 16. Non-functional targets and measurable UI requirements are missing

**References**: Constitution: Validated and Accessible User Workflows; SC-001 through SC-008.

The constitution requires keyboard navigation, accessible labels, progress, and reproducible environments, but the feature spec has no explicit accessibility acceptance criteria, supported browser/viewport requirements, performance targets, or concurrency expectations. SC-001 uses “without manually gathering” and SC-005 says “working page link” without measurable thresholds.

**Clarify**: Set target response/generation times for a representative sprint size, supported browsers/viewports, accessibility conformance target, expected concurrent users, and measurable success criteria. Define whether page URLs are stored as returned by Confluence or constructed from a canonical site URL and page ID.

### 17. Time zones, locale, and report date formatting are unspecified

**References**: FR-010, FR-019, FR-027; Summary Content.

Sprint dates and generation/publication times are required, but their timezone and display format are not defined. Date boundaries also affect the stale-issue rule and the meaning of “most recently closed.”

**Clarify**: Define the canonical storage timezone, display timezone, date format, and tie-breaking behavior for sprints with equal or missing close timestamps.

### 18. Test coverage is described broadly but not bounded

**References**: User-story independent tests; SC-003, SC-007, SC-008; Constitution: Testable Changes.

The spec says tests should cover key behavior but does not define required edge cases for Jira pagination/history, concurrency, failed persistence, publish timeouts, unsafe imported content, permissions, or accessibility. There is no stated CI gate beyond the constitution's general requirement.

**Clarify**: Add a test matrix for the above failure/security cases and name the required checks before merge. Include a sandbox-only manual end-to-end procedure and explicitly prevent routine tests from publishing to production Confluence.

## P2 - Editorial and Product Decisions

### 19. Report history and publication history semantics are not distinguished

**References**: User Story 5; FR-027, FR-029; Assumptions.

The spec describes PostgreSQL report history and Confluence page history but does not say whether history shows every generation, every draft revision, each failed publish attempt, and intentional republish separately, or how long those records remain available.

**Clarify**: Define the history unit, sort/filter behavior, retention, and which actions appear as separate entries. Ensure a failed attempt is not confused with a published page.

### 20. Report overwrite and title collision behavior is undefined

**References**: FR-009, FR-025, FR-026; User Story 2.

The source workflow permits regenerating historical sprints and publishing a new page each time, but the spec does not define duplicate draft names, title collisions, Confluence title uniqueness behavior, or whether a title includes a generation date/version.

**Clarify**: Define draft identity and title collision handling. State whether repeated publication uses the same title, adds a version/date suffix, or allows duplicate titles, while preserving the rule that existing pages are never overwritten.

### 21. Terminology and metadata need finalization

**References**: Feature Branch, Summary, FR-015, FR-026; Project Configuration entity.

The spec alternates “sprint,” “sprint/release,” “report,” and “summary,” and the feature branch remains `TBD`. “Project Name” and “team” are referenced without specifying where they come from or whether they are required. The title uses a hyphen, while the underlying project document may use a different title convention.

**Clarify**: Make V1 terminology sprint-only if release reports are deferred, define required display-name configuration and defaults, settle one title convention, and fill in the branch/status metadata when the feature is scheduled.

## Recommended Resolution Order

1. Decide V1 report scope, user access model, and audience/appendix visibility.
2. Define Jira historical data, issue classification, metrics, and risk rules.
3. Select the summary-generation method and settle service deployment/authentication.
4. Define draft/version behavior, publish idempotency/reconciliation, and data retention.
5. Specify API contracts, Markdown security/compatibility, failure behavior, and measurable non-functional/test criteria.

Until P0 items are answered, implementation should avoid making assumptions that could misstate sprint results, disclose internal issue detail, or create duplicate Confluence pages.
